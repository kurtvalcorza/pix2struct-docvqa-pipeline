## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/pix2struct_docvqa_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `Pix2StructForConditionalGeneration`/`Pix2StructProcessor`. The upstream `pytorch_model.bin` is not listed and not used. **The header font is supplied by the carried module** (`header_font_bytes`, Pillow's bundled Aileron) so the upstream processor's inference-time download of `ybelkada/fonts/Arial.TTF` never happens; the notebook's only external dependencies are the pinned PyPI distributions and the Hub at the model revision.
- **Role stages:** `validate_inputs` writes `outputs/pix2struct_docvqa_input_manifest.json` with the schema (header rendering, patch budget, decoding rule), the ceilings, the input's observed mode and size, the checked questions, the budget, the verdict, and one recorded rejection finding from the blank-question probe; `evaluation_report` writes `outputs/pix2struct_docvqa_evaluation_report.json` — `sample-sanity` with the mean `anls`, the `exact_match` rate and one entry per question on the synthetic form; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 850×1100 invoice-style form rendered in code with Pillow's bundled font — the same page the smoke run used; `anls`/`exact_match` against answers you rendered yourself are sanity evidence for the input contract, header rendering, forward pass and decoding, not a DocVQA metric. The page digest depends on the Pillow build's bundled font rendering and is printed, not asserted.
- Score semantics (UNC1–UNC4): the answer is generated text with no score, probability or correctness signal; the notebook says so before the first answer and again in the interpretation section, and states that the model answers unanswerable questions (blank page → `51759 7951` in the smoke run). The token budget is a caller-owned request parameter exposed as a `# @param` value (default `DEFAULT_MAX_NEW_TOKENS = 32`) and passed explicitly on every `answer` call; `truncated` is surfaced and explained. The notebook performs no validation of its own — image, questions and budget are checked only by the pipeline's `validate_inputs`/`answer` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `MAX_PATCHES` (2048), `MAX_QUESTION_CHARS` (256), `MAX_NEW_TOKENS` (128), `DEFAULT_MAX_NEW_TOKENS` (32) and `DECODING` are printed before the model runs.
- CPU is documented as adequate (card-measured 5.3 s load, 2.3–3.0 s per question on the 850×1100 form; 4.2 s on a 4096×4096 blank page); the notebook states that cost is per question and that GPU output need not match CPU output token-for-token.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
